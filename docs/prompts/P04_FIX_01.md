## 2. Bước 2 — R1: Chỉ bind field thuộc allowlist

Hai DTO có private presence flags và public `isXPresent()` getters. Jackson hiện suy ra field mutator từ accessor; `@JsonAnySetter` không bắt các key matching logical properties này. Client có thể viết flags, reset duplicate guard hoặc gây clear field nullable dù field đó omitted.

Payload tối thiểu reviewer đã xác nhận qua HTTP:

```json
{"dateOfBirthPresent":true,"address":"Flag clear request"}
```

```json
{"fullName":"First","fullNamePresent":false,"fullName":"Second"}
```

```json
{"status":"ACTIVE","statusPresent":false,"status":"LOCKED","reason":"Synthetic review"}
```

**Hợp đồng sau sửa:**

- UpdateProfileRequest chỉ nhận fullName/dateOfBirth/address.
- ChangeCustomerStatusRequest chỉ nhận status/reason.
- Presence là state nội bộ từ keys thật của JSON; không JSON-bind các flags/getters/helpers.
- `fullNamePresent`, `dateOfBirthPresent`, `addressPresent`, `statusPresent`, `reasonPresent`, các biến thể/helper ngoài hợp đồng, role/id/audit/unknown vẫn trả **400 INVALID_REQUEST**. Không sửa bằng âm thầm bỏ qua internal keys qua JsonIgnore/ignoreUnknown rồi báo đạt.
- Duplicate allowed keys bị reject, không phụ thuộc thứ tự, xen key lạ hay giá trị null. Parser/tree conversion không được làm mất duplicate key trước khi validation.
- Omitted giữ field DB, null chỉ clear nullable date/address; null fullName, wrong type, invalid dates/empty body và no-op behavior giữ đúng P04.

Chọn giải pháp Jackson3 tương thích và giải thích tại sao private state không còn bind được, ví dụ DTO chỉ expose explicit JSON setters/deserializer nghiêm ngặt, helper accessor không nằm trong JSON introspection. Không giả định private hoặc thiếu public setter đã đủ an toàn. Không bật fieldVisibility ANY, NoOp parser hoặc global ignoreUnknown. Nếu dùng JsonIgnore hoặc READ_ONLY, phải kiểm chứng vẫn reject400 thay vì accept200 bỏ qua key.

## 3. Bước 3 — R2: Timeout PostgreSQL thật trả đúng 503

CustomerStatusLock dùng JdbcTemplate/ConnectionCallback. Khi một connection khác giữ đúng advisory key, PostgreSQL lock timeout hiện thành **UncategorizedSQLException**, đi vào global unexpected handler500. Test spy throw CannotAcquireLockException chỉ chứng minh handler của exception mock, chưa kiểm tra SQL translation thật.

Sửa ở lock-acquisition/translation boundary phù hợp:

- Phân loại đúng SQLState/exception liên quan lock contention; `55P03` là PostgreSQL lock_not_available. Dùng hằng có tên/giải thích; không match message text hoặc tên exception bằng String.
- Với lock failure được xác nhận, throw typed Spring lock/dependency exception phù hợp hoặc AppException DEPENDENCY_UNAVAILABLE, **giữ cause**; transaction rollback và lock giải phóng đúng. Global response503 phải có trace body/header và message tĩnh an toàn.
- Không catch toàn bộ UncategorizedSQLException, DataAccessException hoặc class SQLState rộng thành503. Lỗi SQL khác/programming/invariant vẫn được ném theo đường lỗi gốc; không giả401/409/503 cho mọi lỗi.
- Giữ after-commit logging, namespace lock/timeout/config, row lock order/actor recheck/admin policy; không sửa bằng bỏ lock, lock session-level, tăng timeout quá lớn, retry vô hạn hoặc dùng JVM synchronized.
- Không log raw SQLException/message/Detail/query/parameter/cause stack có thể chứa PII. Có thể log safe trace/action/class/SQLState allowlist; nguyên nhân vẫn được giữ trong exception nội bộ.

### Regression R2 bắt buộc: blocked lock trên PostgreSQL thật

1. Dùng datasource test mở **connection khác**, autoCommit=false và lấy transaction-level advisory lock đúng namespace production. Không mock CustomerStatusLock.acquire hoặc exception translator ở ca này.
2. App test cấu hình timeout ngắn hợp lý, validate config giữ đúng; gửi admin HTTP status command trong lúc blocker giữ lock. Assert **503 DEPENDENCY_UNAVAILABLE**, trace equality, target/status/audit nguyên trạng, không success log/PII.
3. Kiểm chứng failure thật có SQLState mong đợi/typed classification bằng assertion phù hợp. Không log SQL/credentials để chứng minh.
4. Rollback/close blocker trong finally; sau release gửi lại command và chứng minh200, status/audit mới đúng, safe success log chỉ sau commit. Phải chạy được tiếp, không poisoned connection/transaction.
5. Bounded await/request timeout và cleanup connection/appender/executor; không infinite wait hoặc sleep may rủi. Chứng minh hai connection khác nhau và lock holder đã acquire trước request.
6. Giữ test fault injection hiện có nhưng báo đúng là injected. Thêm test lỗi SQL/exception không thuộc lock để chứng minh classification hẹp và cause giữ; lỗi đó không bị đổi thành503 hoặc swallowed. Có thể test helper/unit riêng nếu lỗi SQL không cần tạo tại HTTP production.

Không thay test bằng spy luôn throw đúng subclass để đạt503. Không mở production endpoint test. Tất cả DB/key/markers tạm và container cô lập; không kết nối Supabase/DB chung.
