## 3. Bước 3 — R2: Cleanup theo completion outcome, không đoán bằng exception type

hasUnknownCommitOutcome hiện nhận mọi Hibernate JDBCException/TransactionSystemException là UNKNOWN. Real row-lock timeout trong findByIdForUpdate callback trước metadata/commit đã rollback nhưng giữ orphan. Existing unknown-outcome test throw ngay tại saveAndFlush callback rồi assert row 0/file 1; đó là rollback đã biết, không commit ambiguity thật.

Thiết kế lại coordinator để giữ receipt/outcome chính xác:

- File write trước DB transaction vẫn receipt-owned theo request; failure trước transaction bắt đầu hoặc callback fail và rollback thành công phải dọn files của request.
- Theo lifecycle/phase transaction có evidence, có thể dùng TransactionSynchronization.afterCompletion với STATUS_COMMITTED/ROLLED_BACK/UNKNOWN kết hợp TransactionTemplate và state ngoài callback. Không quyết định outcome chỉ từ cause class/SQLState hoặc message.
- ROLLED_BACK: cleanup đúng receipt, idempotent; committed: không xóa files kể cả mapper/log/response lỗi sau commit; UNKNOWN thực sự: giữ files/recovery log. Không xóa mọi files khi lỗi SQL, cũng không giữ mọi files vì JDBCException.
- Không catch primary error rồi throw cleanup error thay thế; preserve primary/cause và addSuppressed hợp lý, safe trace/action/receipt logs. Không log raw path/locator/SQL/token/PII. Transaction synchronization failures không được ngầm chuyển outcome sai.
- Callback synchronization phải giữ cleanup failure để coordinator xử lý an toàn; không ném raw exception từ afterCompletion làm framework log stack/cause chứa path hoặc PII. Test log vẫn bắt cả throwable/cause/suppressed và có positive safe event.
- Khi rollback chính nó thất bại hoặc completion statusUNKNOWN, giữ receipt an toàn và ghi limitation. Không claim DB/filesystem fully atomic trong crash/power loss.

Regression bắt buộc:

1. Connection PostgreSQL thứ hai giữ owner row FOR UPDATE. App test có lock_timeout ngắn riêng cho case/context, request HTTP đã qua auth và đã lưu file; real metadata transaction không lấy được row lock. Assert503/trace, callback chưa commit, row 0, file delta 0 sau rollback; release blocker rồi retry201 và files/row khớp. Không mock CannotAcquireLockException để thay đường PostgreSQL thật.
2. Callback sau persist/flush throw TransactionSystemException hoặc Hibernate/SQL error nhưng transaction completionROLLED_BACK: files phải cleanup; cập nhật test hiện đang assert orphan sai.
3. UNKNOWN được fault-inject tại đúng completion/commit boundary hoặc test-controlled transaction manager/synchronization outcome, không ném exception tại callback rồi gọi làUNKNOWN. Assert giữ receipt và safe recovery log, report rõ đây là injected outcome.
4. COMMITTED rồi lỗi sau commit/HTTP mapping: không xóa receipt đã được row tham chiếu; không success claim cho rollback. No dangling metadata/file do coordinator catch rộng.
5. Cleanup failure preserve primary và receipt context; only generated files của request bị xử lý, peer files nguyên trạng.

Không thêm DB table/migration hoặc scheduled sweeper trong lượt sửa. Bộ mới chứng minh outcome thông thường và fault-injected UNKNOWN, không phải mô phỏng power-loss production.
